This is the main operating manual for the submitted project. It explains what
was built, where every part is located, how the native results were produced,
how to repeat the work, and where the implementation intentionally stops.

## 1. Project objective

The repository begins with the official MINIX 3.3.0 release and adds three
configuration-driven experiments:

- four CPU scheduling policies using real child processes;
- configurable hierarchical paging with FIFO and LRU replacement; and
- a real MFS allocation modification that prefers user-defined free-zone runs.

Each requirement has the same reproducibility pattern:

```text
configuration -> validation -> implementation -> native execution
              -> CSV or MFS counters -> deterministic test -> analysis
```

The untouched source is tagged `baseline-v3.3.0`. The current source can be
compared against it with:

```sh
git diff baseline-v3.3.0..HEAD
```

## 2. MINIX architecture relevant to the project

MINIX separates services that a monolithic OS often keeps together. The
microkernel provides low-level scheduling and IPC; servers and commands run as
separate processes. MFS is a user-mode file-system server. This affects what a
safe course experiment can change:

| Requirement | Final implementation boundary |
|---|---|
| Scheduling | User-space policy dispatcher, running real MINIX child processes |
| Paging | Native configurable hierarchy/replacement experiment; x86 MMU remains unchanged |
| Extents | Real modification to the MFS zone-allocation path |

These boundaries must be stated accurately. The project does not claim that a
configuration file can change x86 page-table hardware or that a logical
scheduler dispatch is a measured kernel context switch.

## 4. From clean source to installed MINIX commands

The authoritative build was performed inside the MINIX VM because it provides
the correct headers, libraries, make dialect, and server environment.

```sh
cd /usr/src
make includes

cd /usr/src/minix/commands/schedexperiment
make && make install

cd /usr/src/minix/commands/vmexperiment
make && make install

cd /usr/src/minix/commands/extentexperiment
make && make install

cp /usr/src/etc/scheduler.conf /etc/scheduler.conf
cp /usr/src/etc/paging.conf /etc/paging.conf
cp /usr/src/etc/extent.conf /etc/extent.conf

cd /usr/src/minix/fs/mfs
make && make install
```

The three command Makefiles install both the executable and its matrix script
under `/usr/bin`. `minix/commands/Makefile` and `etc/Makefile` integrate the new
directories and configuration files into the larger MINIX build.

## 5. Correctness gate before collecting results

```sh
cd /usr/src/minix/commands/schedexperiment/tests && sh test_known.sh
cd /usr/src/minix/commands/vmexperiment/tests && sh test_known.sh
cd /usr/src/minix/commands/extentexperiment/tests && sh test_known.sh
```

The scheduling test compares exact average turnaround and waiting values. The
paging test compares exact FIFO and LRU fault counts. The extent test reads back
the generated file and requires zero byte errors. Matrix results were accepted
only after all three gates passed.

## 6. Result lineage

| Evidence | Generated by | Controlled variables | Final size |
|---|---|---|---:|
| `scheduling-matrix.csv` | `run_schedexperiments.sh` | Four quanta, same five jobs | 80 data rows |
| `paging-matrix.csv` | `run_vmexperiments.sh` | 4 page sizes × 3 depths × 3 frame counts × 2 policies | 72 data rows |
| `extent-matrix.csv` | `run_extent_matrix.sh` | 6 extent sizes × 3 repetitions | 18 data rows |
| `native-validation.txt` | Final VM validation procedure | OS identity, PASS lines, counts, checksums, MFS logs | 1 audit log |

The CSV line total shown in the validation log is 173 because the three files
contain 170 data rows and three header rows.

## 7. How the evidence was preserved

After native execution, the three CSV files and validation log were copied from
MINIX into `project-deliverables/native-results/`. Checksums were recorded before
analysis. The report uses these archived values rather than retyping results by
hand. VirtualBox screenshots show the same PASS output and MFS counters.

## 8. Recommended demonstration

Use the known tests for the live correctness demonstration, then show archived
matrices for breadth. Rebuilding MFS or remounting a disk live is slower and
riskier than explaining the already captured native run.

```sh
uname -a
sed -n '1,80p' /etc/scheduler.conf
sed -n '1,80p' /etc/paging.conf
sed -n '1,80p' /etc/extent.conf
sed -n '1,30p' /root/native-validation.txt
```

If Requirement 3 is demonstrated live, verify `/dev/vnd0` is the disposable
image. Never substitute the root or `/usr` device.

## 9. Known limitations and honest interpretation

- Scheduling policies run in a controlled dispatcher, not in the production
  kernel scheduler.
- Paging structures and faults are experimental model values, not hardware MMU
  telemetry. The unreliable legacy VM telemetry fields remain `NA`.
- MFS selects a favorable starting run but does not persist or atomically
  reserve a new extent structure.
- MINIX 3.3 timer resolution rounds some short file-system operations to zero
  microseconds. Those values are not infinite throughput.
- The paging matrix script may terminate a completed `vmexperiment` process
  after its CSV is durably closed because this VM image can spin during libc
  process teardown. It never accepts a case before the complete CSV appears.
